# 같은 계정으로 다른 휴대폰에서 이어하기

2026-10-19 최신 7단계에서 이메일 SDK/계정 화면을 6단계 서버에 연결했다. 본인 기록 조회와 빈 계정에 동의한 최초 가져오기를 제공한다. 현재 전투의 기기 기록/설정은 유지하며 로그인만으로 클라우드 기록을 덮어쓰거나 자동 동기화하지 않는다. 재설정/이메일 변경은 게임 generation을 바꾸지 않고 인증 세션만 폐기한다. 실제 두 휴대폰 전체 이어하기는 계속 미연결/미검증이다. [7단계 결과](EMAIL-AUTH-RESULTS.md)가 아래 이전 단계 상태보다 우선한다.

2026-10-19 6단계에서 본인 기록 조회·빈 계정 최초 가져오기·동의/revision/generation/operationId·충돌 보존을 실제 로컬 Firebase 서버/API로 검증했다. 실제 계정 연결 UI·게스트 파일 업로드·일반 결과/보상 정산·두 휴대폰 전체 동기화는 아직 연결하지 않았다. 기기 설정은 계속 기기에서만 사용하고 개인 설정 API는 향후 선택적 계정 사본 기반이다. [AUTH-BACKEND-RESULTS.md](AUTH-BACKEND-RESULTS.md)의 구현/미검증 구분이 아래 이전 계획보다 우선한다.

2026-10-19 구현 보완: 현재 무료 게스트는 앱 내부의 두 사본에 클리어·해금·최고점수를 저장한다. 서버 동기화로 표시하지 않는다. `account_records.dart`가 아래 기존 충돌 기준의 빈 서버 가져오기 동의·기존 계정 보존·UID/revision/generation·scope 대기열 격리를 모델/fixture로 검증한다. 실제 로그인/서버 adapter·두 기기 동기화는 아직 준비 전이다. [실행 결과](PLAYABLE-RESULTS.md)를 따른다.

2026-10-18 사용자 요청으로 기존 기기 전용 저장 선택을 계정 기반 서버 저장·동기화로 변경했다. 이 문서는 3단계 저장 설계를 유지한다. 4단계에는 Flutter 기본 화면과 이어하기 안내만 작성했으며 서버·동기화 코드·서비스 SDK·운영 리소스는 아직 없다. 현재 실행 결과는 [STAGE4-RESULTS.md](STAGE4-RESULTS.md)를 따른다.

## 저장 범위와 이어하기 기준

| 서버에 저장하는 게임 기록 | 기기별로 유지하는 정보 |
|---|---|
| 클리어/도달 스테이지·다음 시작 체크포인트 | 음량·진동·조작 민감도·이펙트 품질 |
| 최고 점수·해금/선택 기체·영구 강화 | 임시 전투 화면·장식 효과·렌더링 상태 |
| 코인/포인트 잔액·보상 정산·강화 구매 이력의 최소 중복 방지 정보 | UID별 서버 저장본 캐시·서버 미확정 작업 대기열 |

같은 앱 계정으로 로그인하면 해당 계정의 서버 확정 기록을 내려받아 이어한다. 첫 출시의 이어하기 단위는 스테이지 진입/클리어·결과 정산·격납고 변경 체크포인트로 계획한다. 현재 전투를 중단하면 재개 위치가 어디인지 화면에 알린다. 탄환 하나까지 다른 기기에 실시간 복제하는 기능은 범위에 넣지 않는다.

같은 계정은 Firebase의 동일 UID를 의미한다. 같은 이메일처럼 보여도 Kakao/Google/Apple/이메일 로그인이 각각 다른 UID라면 자동으로 합치지 않는다. 기존 인증과 새 공급자 양쪽 소유를 확인해 연결한 뒤 같은 기록에 접근하게 한다. 소셜 이메일이 없어도 공급자 식별자로 연결할 수 있다.

계정 동기화는 기본/구독 사용자의 기록에 공통 제공하며 별도 동기화 상품으로 판매하지 않는다. 로그인 없이 기기 내에서 무료 기본 플레이를 하는 경로에는 다른 기기 복구를 보장하지 않는다. 다른 휴대폰에서 이어하려면 계정 연결·서버 저장 완료·새 기기의 온라인 로그인/다운로드가 필요하다. 구매 복원과 기록 불러오기는 별도 상태다. 다른 OS/스토어의 이용권 공유 조건은 기존 결제 설계와 분리해 10단계에서 확정하며, 저장 기록이 있다고 검증되지 않은 구매를 허용하지 않는다.

## 데이터·서버 경계

기준 구조는 앱/환경이 분리된 Firestore의 사용자별 게임 프로필이다. 서버는 검증한 Auth token의 UID로 경로를 결정하며 요청자가 임의로 보낸 UID를 사용하지 않는다. 게임 프로필·세션/정산 정보·계정/구매 원장을 분리한다.

계획 필드는 schemaVersion·saveGeneration·revision·서버 updatedAt·checkpoint·bestScore·selected/unlockedAircraft·upgradeLevels·wallet·현재 쓰기 세션 epoch/처리 순번이다. 실제 하드웨어 ID·전화번호·연락처·이동 경로·전투 전체 영상은 저장하지 않는다. 앱 버전·스키마 호환을 검사하고 새 스키마를 읽을 수 없는 구버전 앱의 덮어쓰기는 거부한다.

모바일은 이 앱 전용 Functions의 저장 조회/작업 API를 사용하고, Firestore 게임 프로필·재화·정산 원장에 직접 쓰지 않는다. 조회도 본인 저장본만 API로 제공한다. 서버는 정식 계정 연결/필요한 이메일 확인을 검증하고 임시 구매 인증 세션과 클라우드 저장 권한을 구분한다. Security Rules는 직접 접근을 기본 거부하며 Admin SDK 서버에 UID/활성 상태·앱/환경·권한 검증과 최소 IAM을 적용한다. 기록 동기화·인증·구매 검증은 별도 책임이다.

## 오프라인과 충돌 정책

Firestore의 기본 오프라인 문서 충돌은 마지막 쓰기가 이기는 방식이며, 클라이언트 트랜잭션은 오프라인에서 실패한다. 따라서 재화/성장을 캐시 전체 덮어쓰기나 클라이언트 시각으로 병합하지 않고 앱의 로컬 대기열과 서버 트랜잭션을 설계한다. 서버 API의 성공 응답 전 로컬 진행은 '서버 저장 완료'로 표시하지 않는다. [오프라인 동작](https://firebase.google.com/docs/firestore/manage-data/enable-offline), [트랜잭션 제약](https://firebase.google.com/docs/firestore/manage-data/transactions).

1. 온라인 시작: 현재 서버 저장본·revision·generation을 읽고 이어하기 세션을 얻는다. 사용자별 한 기기 쓰기 세션을 기본안으로 두어 동시에 재화를 쓰는 문제를 줄인다. 멀티플레이를 뜻하지 않는다.
2. 체크포인트 저장: operationId·세션 epoch·단조 증가 clientSeq·baseRevision·작업 종류·필요 입력을 보낸다. 서버는 현재 잔액/강화 비용·보상 규칙·기체 해금·스키마·허용 전이를 검증한다. 앱이 보낸 최종 잔액이나 음수 비용을 그대로 신뢰하지 않는다.
3. 원자 처리: 서버 트랜잭션에서 작업 중복 확인·보상 지급/강화 차감·체크포인트·revision 갱신을 함께 수행한다. 응답 유실 후 같은 작업 재전송은 한 번만 반영하고 같은 키의 다른 입력은 거부한다. 거래용 결제 원장과 게임 재화 원장은 섞지 않는다.
4. 오프라인: UID와 세션에 묶인 캐시/대기열에서 진행한다. 화면은 '기기에 저장됨·동기화 대기'로 표시한다. 같은 세션을 유지하고 서버 상태가 호환되면 재연결 시 순서대로 검증/재시도한다. 새 기기에서는 다른 기기의 미전송 진행을 볼 수 없음을 안내한다.
5. 다른 기기에서 이어하기: 새 기기가 최신 서버 저장본을 확인하고 쓰기 세션 인계를 명시적으로 요청한다. 서버가 새 epoch를 발급한 뒤 이전 기기의 쓰기는 거부한다. 이전 기기가 오프라인이었다면 복귀 후 충돌 상태를 보여준다.
6. 충돌: 오래된 기기/다른 epoch/다른 generation의 기록은 자동 덮어쓰거나 잔액·최고 성장만 골라 더하지 않는다. 미전송 원본을 보관하고 서버 확정본과 차이를 설명한 뒤 서버 기록으로 이어할 수 있게 한다. 충돌 분기 자동 병합·오프라인 동시 성장 합산은 첫 출시에서 제공하지 않는다.
7. 순서/재연: 세션별 처리 순번의 high-water mark를 유지해 오래된 작업은 다시 지급하지 않는다. 중복 처리 자료의 정리 후에도 재연이 보상 재지급으로 이어지지 않게 한다. 처리 중 외부 효과는 트랜잭션 재시도 횟수에 따라 중복 실행하지 않는다.

미동기화 기록을 충돌 원본으로 보관했다고 서버 저장/병합이 완료된 것은 아니다. 재시도 한도·대기열 용량·세션/충돌 원본 보관 기간·보상 검증 수준은 구현/운영 측정 후 정하고 공개 전 확정한다. 오프라인 게임의 정당한 플레이를 완벽하게 증명하는 안티치트를 보장하지 않으며, 온라인 순위나 현금 경제를 도입하지 않는다.

## 처음 계정에 연결하거나 계정을 바꿀 때

- 서버에 해당 UID의 기록이 없으면 설명/확인 후 로컬 기록을 최초 가져오기 할 수 있게 한다. 빈 저장본으로 기존 기기 기록을 바로 덮지 않는다. 한 번만 처리되는 import 작업으로 검증한다.
- 서버에 기록이 이미 있으면 두 기록의 저장 시각·진행·보상 차이를 보여주고 원본을 보관한다. 초기 버전은 서버 기록을 기준으로 이어하며 코인·강화·해금을 자동 합산하지 않는다.
- 로그아웃/UID 변경 시 이전 UID 대기열은 새 계정에 전송하지 않는다. 미전송 항목을 안내한 뒤 전송 완료를 기다리거나 삭제를 확인하고, 계정 캐시/화면을 정리한다. 새 로그인 없이 이전 계정의 캐시를 노출하지 않는다.
- 이메일 확인이 필요한 계정은 확인 후 클라우드 연결을 허용한다. 무료 기본 로컬 플레이는 메일 확인을 이유로 없애지 않는다. 구독 만료 시 추가 콘텐츠는 잠기지만 기록·성장 수치·대기열은 삭제하지 않고 기본 구성으로 전환한다. 확인 코드/보안 토큰은 저장 문서나 게임 로그에 넣지 않는다.

## 초기화·탈퇴·백업

'이 기기 캐시 삭제'와 '계정 게임 기록 초기화'를 다른 동작으로 제공한다. 계정 게임 기록 초기화는 최근 재인증·명시적 확인 후 generation을 바꾸고 이전 세션/대기열을 거부한다. 계정 삭제는 활성 접근을 먼저 막고 인증/연결·서버 게임 기록/관련 하위 자료·기기 캐시/대기열을 정리한다. 오프라인 기기에 즉시 지우기 명령을 전달할 수는 없으며 다음 연결에서 삭제/구 generation을 감지해 자동 재업로드를 막는다.

Firestore 부모 문서 삭제만으로 하위 컬렉션이 지워지지 않으므로 서버 삭제 작업은 저장본·정산/세션·충돌/이전 저장본과 하위 자료를 명시적으로 처리하고 잔존 여부를 확인한다. 운영 백업/PITR을 쓴다면 제한된 보관과 복구 시 탈퇴/초기화 재적용 절차를 함께 정한다. 현재 백업·보관 기간·지역은 설정하지 않았다. [Firestore 삭제 동작](https://firebase.google.com/docs/firestore/manage-data/delete-data).

## 단계와 완료 기준

5단계에서는 직렬화 가능한 게임 저장 모델·체크포인트·가상 저장 adapter·손상/중복 정산을 검증한다. 6단계에서 UID별 서버 저장 API·트랜잭션·세션/충돌·동기화 UI를 독립 단위로 구현할 계획이다. 7/8단계 실제 인증 후 같은 UID로 두 휴대폰 복구를 검증하고, 9단계 삭제·초기화 전파, 10단계 구매 복원과 저장 복구의 분리, 11단계 장애/동시 접근을 검증한다.

- [ ] A 기기에서 저장 완료 → 같은 UID의 B 기기에서 진행/기체/성장/재화/점수 일치
- [ ] 다른 UID·다른 앱/환경·미인증·탈퇴 사용자 읽기/쓰기 거부
- [ ] 동일 보상 재전송·응답 유실·순서 역전에도 보상 1회, 강화 비용 원자 차감
- [ ] 두 기기의 같은 잔액 동시 소비·세션 인계·오프라인 오래된 기록 복귀 시 경제 상태 보존
- [ ] 미동기화→저장 중→완료/실패/충돌 UI와 실제 서버 ack 일치
- [ ] 로그아웃/계정 변경·최초 연결·앱 재설치·스키마 변경에서 다른 사용자 기록 유출/덮어쓰기 없음
- [ ] 초기화/탈퇴 이후 오래된 대기열·백업 복원으로 삭제 데이터가 재생성되지 않음

모두 미실행이다. 지역·보관 기간·정기 백업·비용 상한·상세 체크포인트 분량은 도입 단계에서 확인하고, 서비스 가입/유료 플랜·운영 공개는 사용자가 직접 한다.
