# 데이터 처리·보관·권한 계획

## 11단계 현재 대조 — 2026-10-28

최신 SDK 초기화 시점·목적지/항목·삭제/보관·캐시/백업·화면/클립보드·고지 대조는 [STAGE11-DATA-FLOW.md](STAGE11-DATA-FLOW.md)를 따른다. 인증 설정이 있으면 앱 시작의 로그인 복구에서도 Firebase/Auth/App Check를 초기화할 수 있다. 구매는 확인된 앱 계정이 필요하며 게스트 임시 구매는 구현하지 않았다. 아래 이전 단계의 ‘SDK 미설치/미연결’과 전체 동기화 표는 당시 이력/장래 계획이며 현재 구현이나 실연동 완료를 대신하지 않는다.

## 8단계 최신 처리 — 소셜 로컬 구현

Google/Kakao native SDK·Apple AuthenticationServices 브리지로 요청별 proof를 받아 서버 검증 뒤 내부 UID로 연결한다. 이메일/이름/사진을 앱 서버에 복사하거나 이메일로 병합하지 않는다. 공급자 SDK의 기본 처리/attestation 메타데이터까지 ‘수집 없음’으로 표시하지 않는다. 카카오 원본 token은 RAM 전용, 앱 자체 파일/로그에는 provider ID/access/refresh token을 저장하지 않는다. Firebase SDK 세션 유지와 기존 OS 보호 앱 핸들은 분리한다.

앱/환경 전용 `socialChallenges`에는 해시 state/nonce·5분 만료·연결 대상 UID/authEpoch, `socialGrants`에는 검증된 UID/provider subject·1시간 만료, 기존 providers에는 subject 해시 매핑을 둔다. 직접 클라이언트 접근은 거부한다. 논리 만료는 실제 TTL 삭제와 다르며 운영 보관/삭제·공급자 철회/탈퇴는 적용 대기다. 실제 SDK 국외 처리/Keychain/백업·배포 개인정보 고지는 설정 후 직접 검증해야 한다. [결과/라이선스](SOCIAL-AUTH-RESULTS.md), [설정 순서](SOCIAL-SETUP.md). 아래 SDK 미연결 설명은 당시 이력이다.

## 7단계 최신 처리 — 로컬 이메일 연결

공식 FlutterFire Core 5.0.0/Auth 7.0.0/App Check 0.5.0을 추가했다. 가입/재설정 시 비밀번호를 앱 전용 Functions 메모리에서 Firebase로 전달하고 로그인/재인증은 공식 SDK를 사용한다. 앱 자체 DB/파일/로그에 비밀번호·메일 코드·ID/refresh token을 보관하지 않는다. SDK의 플랫폼 인증 유지와 OS 보호 저장소의 앱 세션은 구분한다. 로컬 가상 사용자만 검사했으며 실제 공급자 수집/국외 이전·iOS 잔존/백업 검증은 남아 있다.

서버 `emailLimits`에는 HMAC 처리한 출처/계정 식별자와 제한 횟수/시간, `passwordAccounts`에는 서버 가입 UID/출처/생성 시각을 저장한다. `authEpoch`는 비밀번호/이메일 변경 후 구 세션 접근을 차단한다. 코드의 논리적 제한 만료와 실제 Firestore TTL/삭제 적용은 구분하며 운영 정리·탈퇴 자료 삭제는 이후 단계다. 원본 IP/이메일은 제한 문서에 저장하지 않는다. 비밀번호 거부 목록은 공개 목록의 해시이며 사용자 비밀번호 DB가 아니다. 상세 출처/한계/검사는 [EMAIL-AUTH-RESULTS.md](EMAIL-AUTH-RESULTS.md)를 따른다. 아래 SDK 미설치 문구는 이전 단계 이력이다.

## 6단계 추가 처리 — 로컬 검증, 운영 미연결

`flutter_secure_storage` 11.2.0의 Android native 보호 저장·iOS Keychain 옵션을 앱 세션 기반에 추가했다. UID/불투명 핸들/만료/generation을 이 앱·프로젝트·환경별 키로 보관하며 비밀번호/구매 권한·게임 파일·Firebase refresh token은 저장하지 않는다. 로그인 UI에는 미연결이며 현재 게스트 사용에서 세션을 만들지 않는다. 원본 파일/기기 설정 자동 업로드는 없다.

`server/firebase`는 가상 UID·provider subject 매핑·해시 세션·가져온 진행/최고점수·설정·중복 작업 자료를 로컬 Auth/Firestore/Functions에서 처리한다. 테스트 데이터는 example.test 가상 사용자뿐이고 실제 클라우드/운영 사용자는 없다. 운영 전 세션/작업 자료 정리·계정 하위 자료 삭제·보관 근거/기간·백업과 IAM을 확정해야 한다. Firebase Auth의 실제 처리는 공식 설명상 미국이며 서울 DB 후보와 구분한다. [공식 위치/처리 항목](https://firebase.google.com/support/privacy), [6단계 결과](AUTH-BACKEND-RESULTS.md).

아래 ‘인증 SDK 미설치’는 모바일 Firebase SDK를 뜻하며 새 서버 Admin SDK와 OS 보호 저장소를 포함하는 설명은 아니다. App Check attestation/공급자 메타데이터·토큰 유지/갱신·실제 로그인/구매/삭제의 운영 처리는 미검증이다.

## 2026-10-19 실제 로컬 처리 보완

아래 기존 표는 미래 서비스 설계다. 현재 인증/결제/분석 SDK는 설치하지 않았다. path_provider 2.1.6은 앱 지원 경로, audioplayers 6.8.1은 내장 음향, url_launcher 6.3.3은 허용된 외부 링크, package_info_plus 10.2.2는 앱 버전 조회에 사용한다. 유지관리자 소스·manifest/빌드를 검토했으나 네트워크 패킷/모든 전이 의존성의 운영 검증 완료를 뜻하지 않는다.

현재 추가한 Android INTERNET은 구성된 협동 WSS 통신용 정상 권한이며 민감 런타임 권한 요청이 아니다. cleartext 금지·TLS 인증서 검증·백업 제외를 유지했다. 실제 인증/결제 서비스를 연결하면 처리표·국외 이전·스토어 고지와 선택 분석 동의를 다시 대조해야 한다.

아래는 실제 서비스 연결 이후의 설계안이다. 4단계에는 Flutter 기본 화면만 생성했으며 인증·결제·서버 SDK는 설치하지 않았다. 네트워크 캡처로 서비스 SDK 동작을 검증한 것은 아니므로 '수집 데이터 없음' 또는 특정 SDK가 아무 데이터도 전송하지 않는다고 선언하지 않는다. 현재 폼의 메모리 처리·권한·보호 저장소 검토는 [STAGE4-RESULTS.md](STAGE4-RESULTS.md)를 따른다. 실제 공급자 처리 지역·계약·국외 이전·보관·SDK 목록은 채택/공개 전 확인한다.

## 삭제와 보관의 완료 기준

7일·30일은 현재 운영 목표 초안이며 법이 정한 기간이나 이미 적용된 운영 약속으로 표시하지 않는다. 실제 개인정보처리자·출시 국가·사업 형태가 아직 미정이므로 거래/세무/분쟁/남용 방지에 어떤 자료를 얼마 동안 보관해야 하는지 근거를 확인한 뒤 공개 문안을 확정한다. 구매 관련이라는 이유로 모든 데이터 무기한 보관을 허용하지 않는다. 근거·기간이 정해지지 않은 예외는 출시 전 미완료 항목이다.

계정 삭제 시 활성 접근 차단 → provider 철회/연결 해제 → 클라우드 게임 기록·정산/세션·충돌/이전 저장본 및 관련 하위 자료·계정 삭제 → 기기 캐시/대기열 정리 → 완료/재시도 확인을 검증한다. 부모 문서만 지워 하위 데이터가 남지 않도록 서버 작업으로 잔존 여부를 확인한다. 운영 백업을 복구할 때도 탈퇴/초기화 상태를 재적용한다. 앱 삭제가 서버 계정 삭제나 스토어 환불을 의미하지 않는다. 다른 오프라인 기기는 재연결 때 삭제/generation을 감지하며 오래된 기록을 다시 업로드하지 않게 한다.

서로 다른 UID의 기록은 자동 병합하지 않고 같은 UID의 동기화만 허용한다. 기기 설정과 게임 저장 캐시를 구분하고 저장 파일의 버전·정상 저장본·원자적 갱신·작업 중복 방지를 설계한다. 계정 전환 때 이전 UID의 화면/캐시/대기열이 새 계정으로 넘어가지 않게 한다. 클라이언트 시각이나 잔액 max/합산으로 충돌을 해결하지 않는다. 시스템 백업·서버 백업의 대상/기간/접근 통제를 정하며 미전송 데이터는 서버 복구 가능 자료로 표시하지 않는다. 오프라인 세이브 조작을 완전히 막는다고 보장하지 않고 온라인 거래/랭킹 경제를 도입하지 않는다. 상세 처리는 [CLOUD-SAVE.md](CLOUD-SAVE.md)에 있다.
